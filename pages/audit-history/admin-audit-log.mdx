# Admin audit log

The `audit_log` table captures sensitive admin actions: user-role changes, material edits, quarantine flips, supplier-contact updates, and other operations that affect downstream behavior.

## What gets logged

| Action class | Example |
|---|---|
| `user.role.changed` | Promoting an operator to manager |
| `user.invited` | Sending a new-user invite |
| `material.updated` | Changing default kerf for a material |
| `roll.quarantined` | Manually flagging a roll for defect |
| `roll.unquarantined` | Releasing a quarantined roll |
| `supplier.updated` | Editing supplier contact info |
| `purchase_order.cancelled` | Cancelling a sent PO |
| `job.cancelled` | Cancelling a job (any operator+) |
| `cut.voided` | Voiding a cut history row (super_admin only) |
| `workspace.settings.updated` | Changing units, timezone, branding |

## The audit record

`audit_log`:

| Column | Notes |
|---|---|
| `id` | UUID |
| `actor_id` | FK to the user who took the action |
| `action` | One of the action classes above |
| `resource_type` | `user` / `roll` / `material` / etc. |
| `resource_id` | The UUID of the affected entity |
| `before_value` | JSONB snapshot of the row before the action |
| `after_value` | JSONB snapshot after |
| `ip_address` | The IP the action came from |
| `user_agent` | The browser/client UA string |
| `created_at` | UTC timestamp |

`before_value` and `after_value` are full row snapshots — not diffs — so a future schema change can't break a query against historical entries.

## RLS-protected

The audit log is itself protected by row-level security. Only `super_admin` can read the table; everyone else gets zero rows.

This is intentional. The audit log is a defense against bad actors, including bad-actor admins. A `super_admin` removing entries from the audit log generates its own audit-log entry that another `super_admin` can see — there is no clean way to cover tracks.

<Callout type="warning">
Don't try to use the audit log as a general-purpose change-tracking table for application features. It's intentionally narrow. Use database history extensions (e.g., `pgaudit`) or application-level event logs for broader use cases.
</Callout>

## Querying

```sql
-- All role changes in the last 90 days
SELECT a.created_at, actor.email AS actor, target.email AS target,
       a.before_value->'role' AS old_role, a.after_value->'role' AS new_role
FROM audit_log a
JOIN auth.users actor ON actor.id = a.actor_id
JOIN auth.users target ON target.id = a.resource_id
WHERE a.action = 'user.role.changed'
  AND a.created_at > NOW() - INTERVAL '90 days'
ORDER BY a.created_at DESC;
```

## Retention

Audit log rows are never auto-deleted. SOC 2 will require a documented retention policy; the planned policy is "indefinite for compliance, with archive-tiered storage after 2 years." See [SOC 2 roadmap](/security/soc2-roadmap).
